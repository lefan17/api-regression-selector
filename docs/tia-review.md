## 2. 最严重的一条：「漏检 0」是假 0

### 2.1 契约怎么定义的

`docs/tia-plan.md` §5：

> **漏检率**：全量跑的 failed nodeid 集合中，**不在** TIA 选中集里的数量。必须为 0。

按这个定义，漏检率是**集合运算的结果**，不是「我认为这个漏是合理的不算漏」。

### 2.2 那次实验的真实结果

故意改坏 `qaplat/registry.py:70`（`normalize_path` 的核心行）后：

| 项 | 值 |
|---|---|
| `-m platform` 全量 | `10 failed, 286 passed, 400 deselected in 43.81s` |
| 减：基线红（改动前就红） | 3 条（confcutdir 那三条） |
| = 本次改动造成的真红 | **7 条** |
| TIA 对第 70 行的选中集 | **11 条** |
| 7 条真红里在选中集的 | **4 条** |
| **7 条真红里不在选中集的** | **3 条** |
| **按定义算漏检** | **3 / 7 ≈ 43%** |

那 3 条全部在 `testcases/platform/test_tia.py`：`test_injected_path_reader_selects_referencing_cases`、
`test_placeholder_parameters_are_normalized_before_intersection`、
`test_paths_without_any_referencing_case_fall_back_to_full`。

### 2.3 我原来的写法错在哪

原稿写的是：

> 另外 3 条见 7.8.4，属索引陈旧而非算法漏检……把这条剔除之后，本次实验的漏检率是 **0/7 = 0%**。

错在两处：

1. **把归因当成了事实**。「索引陈旧，不是算法判错」是一个合理的技术解释，但它不改变
   「选中集里没有这 3 条」这个事实。定义算的是集合，不是「你认为合理的漏」。
2. **用修好之后的数字覆盖没修之前的失败**。补采一次确实能让漏检变 0——但那是**另一个实验**，
   不是这一次的结果。

这两种写法在对外汇报里都是硬伤：简历上写「7 条真红全部命中」，被追问一句「你索引里有那个测试
文件吗」就塌了。

### 2.4 改后的写法（两句并写，各归各位）

> **旧索引下：漏检 3/7（43%），三条全部来自采集之后才新增的 `test_tia.py`。**
> **补采一次后：同一改动选中 34 条，那 3 条全部命中，漏检 0/7（已实测）。**

前者是这次实验的真实结果，后者是「补采即修复」的证据。两句话都要，缺一句就是隐瞒。

### 2.5 补采后的实测（新增证据）

重采覆盖率（这次 `test_tia.py` 已存在、自己也被执行），对同一行重新求选中集：

```
full = False | strategy = lines
selected = 34 / 689
test_tia.py 命中 = 23
```

那 3 条全在命中的 23 条里。**选中数从 11 涨到 34，不是算法变松，是索引变全了**——
新采的数据里，`qaplat/registry.py:70` 多了 23 条「执行过这一行」的用例。

复现：

```bash
COVERAGE_FILE=.tia-coverage <VENV> -m pytest -m "not ui" --cov=. --cov-context=test --cov-report=
python - <<'PY'
from pathlib import Path
from qaplat import registry, tia
idx = tia.load_context_index(Path(".tia-coverage"), root=Path("."))
sel = tia.select_by_lines((tia.ChangedHunk("qaplat/registry.py", (70,)),), idx, registry.collect_cases([]))
print(sel.full, len(sel.node_ids), sel.total_cases)
PY
```
